# VolcanoX — Implementation Guide

This is the companion to `PRD_MoltenGround.md` §0. The PRD says *what* is
being built and *why*; this document says *how it's put together* and *how
to build/run/extend it*. Read this before touching the code.

| Phase | Covers | Status |
|---|---|---|
| **1 — Objects** | Geometry, placement, transform-driven motion, flat colours | **Built** (§1–§8) |
| **1b — Time of day, cameras, control** | Automatic day/night cycle, views from the drones, a keyboard-controlled drone | **Built.** Spec in §10 (see its as-built notes); results in §8 |
| **2 — Illumination, shading, texture** | Phong lighting, Flat/Gouraud/Phong switch, procedural textures, HUD | **Built.** Spec in §9 (see its as-built notes); results in §8 |
| **3 — Ray tracing (stretch)** | Camera-ray shadows and reflections in the fragment shader; inverse (light-ray) tracing of lava glow into a light map | **Built.** Spec in §11 (see its as-built notes); results in §8 |

> **Naming.** The project is **VolcanoX** (the title submitted in the KUET
> CSE 4102 lab proposal). "Molten Ground" was an early working title that
> survives only in the PRD's filename, `PRD_MoltenGround.md`. This guide
> refers to the file by its real name so the links work.

> **The code is the reference.** The code had moved past the PRD (more lava
> flows, orbiting drones, a storm-cloud lightning rework, the whole
> `Environment.cpp` setting). Those changes are kept. PRD v1.2 was rewritten on
> 2026-10-09 to describe the code as it is, and this guide and the PRD now
> agree. §7 lists the implemented state of every object.

## 1. What stage this is

**All four phases are built** (dated 2026-10-09). Phase 1 drew objects only, with
flat colours. On top of it the code now has an automatic day/night clock, views
through the drones' cameras, a keyboard-flown drone (1b); Phong illumination, the
Flat/Gouraud/Phong switch, procedural textures and a HUD (2); and ray-traced
shadows and reflections plus inverse (light-ray) tracing of the lava glow (3).
§9, §10 and §11 keep their original wording as the specification; each opens with
an **"As built"** list of the places where the code differs from it.

**Phase 2 is the three things the project is graded on, and §9 specifies
all of them:**
1. **Illumination** — ambient + diffuse + specular, a distance-attenuated
   crater point light plus a directional sky light (moon at night, sun by day),
   per-material coefficients (PRD §11, §13).
2. **Shading** — a live Flat / Gouraud / Phong switch (PRD §12).
3. **Texture** — procedurally generated textures that modulate the surface
   colour (§9.3). This one is new relative to the PRD and the proposal; see
   the scope note below.

They go on top of the exact same object functions Phase 1 built. This is the
part the lab proposal is mostly about, so it is required work, not polish.

**Phase 1b (§10) adds three features that don't depend on lighting:** an
automatic **day/night cycle**, **camera views from the drones**, and
**controllable objects** (a keyboard-flown drone, optionally a ground rover).

**Still out of scope:** shadow *mapping*, post-processing, and a
collision/physics system (PRD §3.2). Shadows and reflections are no longer
banned: they are allowed only through the ray-tracing mode in §11, as a stretch
tier on top of the MVP, and that reverses a promise in the submitted proposal
(see the scope warning at the top of §11). Don't add them any other way, and
not in Phase 2 or 1b.

> **Scope note — textures.** The submitted proposal says *"No textures or
> pre-made models will be used"* and PRD §3.2 lists textures as a non-goal
> ("hides the shading model you're being graded on"). Texture is being added
> anyway, so §9.3 keeps it as close to the original intent as possible:
> textures are **generated by code at startup** (no image files, no loader
> library, no pre-made assets), they modulate only the diffuse/ambient colour
> (never specular or emission), and a key turns them off. The PRD, the
> proposal summary in the report, and the traceability matrix need a matching
> update. See §7, decision 4.

## 2. Toolchain (and the one gotcha that cost the most time)

This lab machine has:
- **GLFW** and **GLEW** installed via MSYS2 (`C:\msys64\mingw64`) — used as
  the window/input library and the OpenGL function loader (GLEW instead of
  GLAD, since GLAD wasn't installed and there's no package manager here to
  fetch it — see PRD §0.1).
- **No GLM** and **no CMake binary**. Rather than depend on a network
  package manager, the project uses `src/MathUtils.h` (a small hand-written
  vector/matrix header covering exactly what this project needs) in place of
  GLM, and a direct `g++` build script in place of CMake.
- **Two different MinGW installs on this machine**: an older one bundled
  with Code::Blocks (`C:\Program Files\CodeBlocks\MinGW`) and the MSYS2 one
  (`C:\msys64\mingw64`). This matters a lot — see below.

### The gotcha: always build with MSYS2's `mingw64\bin` first in PATH

If you compile with whatever `g++` your shell finds first, and the
Code::Blocks MinGW directory comes before `C:\msys64\mingw64\bin` in `PATH`,
**the compiler silently fails** (`cc1plus.exe` crashes with no error message
at all — exit code 1, empty stdout/stderr) because it loads an incompatible
DLL of the same name from the wrong MinGW install. The fix is simple but
non-obvious: put `C:\msys64\mingw64\bin` at the **front** of `PATH` for the
build, e.g. in PowerShell:

```powershell
$env:PATH = "C:\msys64\mingw64\bin;" + $env:PATH
```

The provided `build.ps1` does this for you.

A second, related issue: even once it compiles, an executable that
dynamically links `libstdc++-6.dll` / `libgcc_s_seh-1.dll` /
`libwinpthread-1.dll` will pick up whichever copy of those DLLs `PATH`
resolves to *at run time* — which, on this machine, is the incompatible
Code::Blocks copy, causing an "Entry Point Not Found" dialog when launched
outside a PATH-corrected shell (e.g. double-clicked from Explorer, or run
from the grader's own shell). **Always build with
`-static -static-libgcc -static-libstdc++`** so the shipped `.exe` has no
runtime DLL dependency on `PATH` at all. `build.ps1` already does this.

## 3. Building

```powershell
./build.ps1
```

This runs (with `mingw64\bin` prioritized in `PATH`):

```powershell
g++ -std=c++17 -O2 -DGLEW_STATIC -I"C:\msys64\mingw64\include" -Isrc `
    src/main.cpp src/Shader.cpp src/Geometry.cpp src/SceneObjects.cpp `
    src/NewObjects.cpp src/Environment.cpp src/Texture.cpp `
    -L"C:\msys64\mingw64\lib" -static -static-libgcc -static-libstdc++ `
    -lglew32 -lglfw3 -lopengl32 -lgdi32 -o build/VolcanoX.exe
```

producing `build/VolcanoX.exe`, then copies `shaders/` to `build/shaders/`.
A `CMakeLists.txt` is also provided for a machine that does have CMake
(e.g. the grader's), using `find_package` for GLFW/GLEW/OpenGL the normal
way. **If you add a `.cpp` file, add it to both `build.ps1` and
`CMakeLists.txt`.**

## 4. Running

```powershell
./build/VolcanoX.exe
```

Run it from the project root. The shaders are loaded from disk at
`shaders/basic.vert` / `shaders/basic.frag` relative to the working
directory. `build.ps1` also copies them to `build/shaders/`, so launching
from inside `build/` works too.

### Controls (all implemented)

This is the single key map. The camera is a simple discrete-key orbit camera
(`src/Camera.h`), deliberately not a mouse-look FPS camera, so a lab demo never
depends on cursor capture behaving correctly on the grader's machine. It also
resolves the old conflict: `+`/`-` zoom the camera today, but they are needed for tessellation,
and the keys that drive an object must not be letters (the first version used `W`/`A`/`S`/`D`; it
was changed to the arrow keys on 2026-10-11 because `S` was hard to type). So **zoom moves to the mouse
wheel and `PgUp`/`PgDn`**, and the arrow keys orbit the camera only while nothing is controlled.

Toggle and cycle keys (`N`, `C`, `V`, `Tab`, `P`, `T`, `H`, `R`, `F`, `M`, `1`–`3`, `L`, `K`, `B`, `+`, `-`)
use a key-press **callback**, not polling in `processInput`, or one tap
cycles many times per frame. Held keys (arrows, piloting) use polling.

### How an object is built

Every object function follows the same recipe:
1. Look up the pre-built primitive mesh(es) it needs from `MeshLibrary`
   (built once at startup in `MeshLibrary::build()`).
2. Compute a `Mat4` model matrix per part as `T * R * S` (translate, then
   rotate, then scale — matrix multiplication order matters: the rightmost
   matrix is applied to the vertex first).
3. Call `setModel(sh, model)` (sets `uModel` and the normal matrix),
   `sh.setVec4("uColor", r,g,b,a)`, then `mesh.draw()`. The material and the
   texture are set once per group of draws in `renderScene()` (`uMat`, `uTexId`).

For example, a burnt tree's trunk (`NewObjects.cpp`, `drawBurntTree`):
```cpp
Mat4 trunkModel = base * Mat4::scale(Vec3(trunkRadius, trunkHeight, trunkRadius));
drawMeshLocal(sh, lib.cone, trunkModel, r, g, b);
```
where `base` already carries the tree's world position, its lean rotation,
and a random facing rotation.

### Adding a new object

1. Decide which existing primitive(s) in `Geometry.h`/`MeshLibrary` it needs
   (cone, cylinder, sphere, box, disc, rock, line/bolt). Only add a new
   primitive generator if none of those fit.
2. Write `drawYourObject(const Shader&, const MeshLibrary&, <placement params>)`
   in `NewObjects.cpp`, following the recipe above.
3. Declare it in `SceneObjects.h`.
4. Call it from the render loop in `main.cpp`, passing whatever position/
   scale/rotation you want — placement is entirely the caller's decision,
   the function itself has no hardcoded world position.
5. Before adding it, check PRD §2: *"If a feature doesn't map to a row in
   Section 4, it doesn't get built."* Also add a row to the object
   inventory (§6 below).

### Particle pools (droplets / rock chunks / ash puffs)

These use fixed-size arrays of "slots" with `static` storage inside their
`updateAndDrawX()` function (see `SceneObjects.cpp`). Every field (position,
scale, color, alpha) is a **closed-form function of `age = now - spawnTime`**
— nothing is stored frame-to-frame except `spawnTime` and the initial
velocity/seed. An inactive slot is simply skipped when drawing. This matches
the PRD's "no pre-baked animation" requirement and is what to imitate if you
add another pooled/recurring object later.

Current pool sizes: **8** droplets, **6** ash puffs, **36** rock chunks. These
are the accepted sizes; PRD v1.2 §3.3 now says the same.

**Draw-call budget (measured).** `--bench` reports about **800 draw calls per frame by day and
1000–1300 at night** (the night count is higher because the droplets and ash puffs are active,
and the lava flows are built from up to ~110 boxes each). The lab machine runs about **240 FPS**
with vsync off (§8). PRD §14's frame-rate target is therefore met with a large margin.

**Decisions taken (2026-10-09).**
1. *Keep everything implemented.* The environment scenery, five lava flows,
   36 rock chunks, two orbiting drones and the reworked lightning all stay.
   The PRD was changed to match, not the code.
2. *Base pool: re-enabled, in a new place.* The plan was to do the Gouraud-vs-Phong
   highlight demo (PRD §12.2 Demo A) on the crater glow disc. That fails on geometry:
   the disc is small and its crater light sits in the disc's own plane, so no
   highlight ever forms on it. The fallback was the existing `drawLavaPool`, which
   is now called again. It first sat at the foot of the river (the river's boxes covered
   it), then alone at `(-44, 0.1, 6)`, where it read as a flat orange disc with no lava
   leading to it, so it now sits at the end of the sheet flow and only fills once the flow
   arrives (§14.1). It is the one lava element added back after "keep everything
   implemented".
3. *Wind indicators stay removed;* the drone flight path stays.
4. *Textures are a scope change* against the proposal. The PRD was updated
   (§3.2, §4, §10, §14). In the report, state that textures are generated
   procedurally with no image files, so "no pre-made models or assets" still
   holds. Textures are in neither the L8 nor the L9 deck, so they have no
   lecture row to cite; justify them as a supporting feature.
5. *Day/night, drone cameras and controllable objects are new scope,* added to
   the PRD (§3.1, §4, §9.7–§9.9, §10) and specified in §10 here.
6. *Ray tracing reverses the proposal's "no shadows or reflections".* It is a stretch tier (§11), built only after the MVP, with the raster pipeline as the main renderer. PRD v1.3 was updated to match. The report must say so plainly.

## 8. What's verified

(a PPM screenshot rendered at a fixed 1/60 s step, converted to PNG and looked at)
and `--bench`. Interactive keyboard input could not be driven from a script, so the
**key handling is untested by hand**: the key callbacks just set the same state the

- The `.exe` imports only Windows system DLLs (`GDI32`, `KERNEL32`, `OPENGL32`, `SHELL32`,
  `USER32`, `msvcrt`) and renders correctly with `PATH` reduced to `C:\Windows`: the §2
  requirement holds.
- No GL errors in the nine configurations checked with the GL error query: terms 0, 1 and 2;
  crater-only and sky-only lights; Blinn; Flat with shadows; Gouraud with shadows,
  reflections and lava-light tracing; and the pilot camera with all of those on.

**Phase 1b**

**Built.** This section is the specification; the code differs in these places.

**As built**
- *Vertex format.* Interleaved `x,y,z, nx,ny,nz, u,v` as specified. Normals use the L9
  averaging inside smoothing groups. Every mesh is also wound counter-clockwise from outside,
  so back-face culling is **on** (the sky dome turns it off locally).
- *Two original bugs fixed on the way.* The sphere generator left a hole at each pole

- *Textures:* a `uTexId` per group, `uTexScale` for the repeats, three 256×256 textures with
  mean 0.5 (the shader multiplies the albedo by `2 × texel`). The ash texture has no low
  frequencies so its tiling isn't obvious on the large ground disc.
- *HUD:* a 5×7 bitmap font (upper case only) drawn on one batched draw call, with a key legend

### 9.1 Illumination (PRD §11, §13)

The model is the L8 Phong illumination equation, evaluated per surface
point, with two lights summed:

```
I = I_e                                              // emission  (lava, crater glow only)
  + k_a · I_a_global                                 // ambient
  + Σ_lights  f_att(d) · [ k_d · I_d · max(0, N·L)   // diffuse
                         + k_s · I_s · max(0, R·V)^n_s ]   // specular
R = reflect(−L, N)            (Blinn-Phong option: (N·H)^n_s, H = normalize(L+V))
```

| Light | Type | Parameters |
|---|---|---|
| **Light 0 — crater glow** | Point, at `craterPos`, dominant | `f_att = 1/(1.0 + 0.06·d + 0.02·d²)`; `I_d = (1.0, 0.45, 0.15)`, `I_s = (1.0, 0.6, 0.3)` |
| **Light 1 — sky light** (moon at night, sun by day) | Directional. Night values below; direction and colour blend toward the sun by day (§10.1) | No attenuation. Night: `L = −normalize(−0.3, −0.6, 0.4)`, `I_d = (0.12, 0.14, 0.20)`, `I_s = (0.15, 0.16, 0.18)` |
| **Global ambient** | — | Night: `I_a_global = (0.04, 0.04, 0.06)`. Raised by day (§10.1) |

The scene still has exactly two lights: the crater, and one directional sky
light whose direction and colour follow the time of day.

**Materials.** The PRD defines three, chosen so the frame spans `n_s` = 2 → 140:

| Material | `k_a` | `k_d` | `k_s` | `n_s` | Emission |
|---|---|---|---|---|---|
| Rock (also rim rocks) | (0.05, 0.04, 0.04) | (0.25, 0.20, 0.18) | (0.05, 0.05, 0.05) | 4 | — |
| Lava (droplets, flows, pool) | (0.30, 0.05, 0.00) | (0.90, 0.25, 0.05) | (0.95, 0.85, 0.60) | 140 | (1.0, 0.4, 0.05) × cooling factor |
| Ash | (0.08, 0.08, 0.09) | (0.35, 0.34, 0.32) | (0.05, 0.05, 0.05) | 2 | — |

**Everything else needs a rule, because the PRD doesn't give one.** The scene
also has trees, the hut, the windmill, the drones, terrain, clouds, sky, stars
and lightning. Suggested defaults:
- *Lit, matte* (trees, hut, windmill, drone, terrain, hills, mountains, ground):
  derive from the object's existing colour, `k_d = colour`, `k_a = 0.2·colour`,
  `k_s = 0.05`, `n_s = 4`. Existing colours then carry over unchanged.
- *Unlit* (sky dome, stars, moon, lightning bolts, storm clouds): a `uUnlit`
  flag skips the lighting math and outputs the colour as today. Storm clouds
  are the one to look at: they are meant to flash with `lightningFlash()`.
- *Emissive* (crater glow disc, lava): emission term; the crater glow's
  `0.85 + 0.15·sin(3t)` pulse and the lava flows' travelling pulse become the
  emission scale. This replaces the CPU-computed colour pulse in
  `drawLavaFlow` (PRD §9.3).
- *Translucent* (ash puffs, ash cloud): lit as usual, alpha kept so the
  existing blending still works.

Attenuation is what the demo checks: orbit away from the crater and the rock
must visibly darken as the distance readout climbs. If the whole scene is
too dark or too flat, tune `a₀, a₁, a₂` first (PRD §15).

### 9.2 Shading (PRD §12)

Three modes in **one** shader program, selected by `uniform int uShadingMode`
and switched live with keys `1` / `2` / `3`. The same illumination equation
runs in all three. Only *where* it runs, and which normal it sees, differs:

| Mode | Key | Where lighting is evaluated | Normal used |
|---|---|---|---|
| 0 — Flat | `1` | Fragment shader | `normalize(cross(dFdx(FragPos), dFdy(FragPos)))`: one normal per triangle |
| 1 — Gouraud | `2` | **Vertex shader**; colour interpolated across the face | Per-vertex (averaged) normal |
| 2 — Phong (default) | `3` | **Fragment shader**, per pixel | Per-vertex normal, interpolated then re-normalised |

**Splitting the lighting term so it composes with textures.** Compute the
lighting as two separate vectors: `lightDiffuse` (ambient + diffuse sum, with
the albedo factored out) and `lightSpecular`. Final colour:

```
colour = emission + albedo · texel · lightDiffuse + lightSpecular
```

In Gouraud mode the vertex shader outputs `lightDiffuse` and `lightSpecular`
and the fragment shader applies `albedo · texel` after interpolation. This
keeps texture working in every mode, and keeps specular untouched by it.

**Run these two demos with ray tracing off (`R`).** With it on, Gouraud is evaluated per fragment (§11.3) and looks like Phong, which would hide the very difference being shown.

**The two demonstrations that must work** (they are why the modes exist):
- *Demo A — Gouraud loses the highlight.* On the **lava pool** at low tessellation (4
  segments; `+`/`-` rebuild it), with the camera near the sun's mirror angle: Gouraud shows
  the highlight as a diamond of linear interpolation between the vertices (or loses it
  between them), while Phong keeps a smooth glint (L9 slide 28). The glint is a point on the
  plane, not a surface patch, so orbit until it lands on the pool. By day it is brightest.
- *Demo B — Mach banding.* The volcano cone at low segment count in Flat mode
  (L9 slides 13–15). **Take the screenshot with textures off (`T`)**, because
  a texture hides the banding.

**Vertex normals** are required by every mode except Flat. The L9 slide 20
averaging goes in the cone and rock generators:

```
N_v = (Σ N_i) / ‖Σ N_i‖        // sum the face normals meeting at a shared vertex, then normalise
```

Two gotchas: `Geometry::box` must emit **separate vertices per face** (24, not
8) or its corners get averaged normals and look rounded. And the sphere's
normal is simply its position (it is unit-radius at the origin).

### 9.3 Texture (new; see the scope note in §1 and §7, decision 4)

**Approach: procedural textures, generated in code at startup.** No image
files and no loader library (no `stb_image`); this keeps the proposal's "no
pre-made models, everything explainable by a formula" intact. Each texture is a
256×256 RGB byte array filled with value noise or a pattern formula (reusing
`hashNoise` from `MathUtils.h`), uploaded once with `glTexImage2D`.

| Texture | Pattern | Used on |
|---|---|---|
| `rockNoise` | Multi-octave value noise, dark grey-brown | Volcano cone, rim rocks, rock chunks, mountains |
| `groundAsh` | Fine noise with darker blotches | Terrain discs and the ground plane |
| `woodGrain` | Stretched noise / stripe pattern | Tree trunks, hut walls, windmill |

Lava, sky, stars, lightning and clouds stay untextured. Lava in particular
must stay a clean `n_s` = 140 surface for the material-contrast demo.

**Mechanics.**
- *UVs.* Add a `vec2` UV to every mesh that gets a texture. Cone/cylinder/volcano:
  `u = angle/2π`, `v = height`. Sphere: latitude/longitude. Box: `0..1` per face.
  Disc: planar from `x, z`. Rock: spherical projection from the unit position.
- *Sampling.* `GL_REPEAT` wrap, `GL_LINEAR_MIPMAP_LINEAR` minification with
  `glGenerateMipmap`, `GL_LINEAR` magnification. All fine on GL 3.3 core.
  A per-draw `uTexScale` controls tiling (the terrain needs far more repeats
  than a tree trunk).
- *Where it applies.* The texel multiplies **only** the albedo (`k_d` and
  `k_a`). It never touches `k_s` or emission, so the highlights stay legible
  and Phong vs Gouraud remains visible on a textured surface.
- *The off switch.* Key `T` sets `uUseTex = 0` globally. PRD §3.2 rejected
  textures because they can hide the shading model being graded; this switch is
  what answers that. Keep it in the demo script.
- *Also used by the HUD.* The HUD's bitmap font (§9.5) is a small texture drawn
  on screen-space quads, so the texture upload code is shared.

## 10. Phase 1b — Time of day, drone cameras, controllable objects

**Built.** This section is the specification; the code differs in these places.

**As built**
- *Sun and moon directions.* The sun and moon sweep a great circle spanned by the default
  camera's right vector `R = (0.82, 0, -0.57)` and up, with a weight on the default view
  direction `F = (-0.57, 0, -0.82)`: `sunDir = normalize(cosθ·R + sinθ·U − 0.2·F)` and
  `moonDir = normalize(−cosθ·R − sinθ·U + 1.3·F)`. The moon is **not exactly opposite** the sun:
  both rise and set on the camera-facing side. The moon sits in front of the default camera, so
  it is in view at night; the sun sits slightly behind the view plane, so the camera-facing sides of
  objects are lit by day (a sun in front would backlight everything). The sun is visible when
  you orbit the camera round to face it.
- *Lock levels.* A lock eases the daylight, the sun and moon directions, and the sky together,
  over 1.5 s. The locked hours are 10:00 (day) and 22:00 (night).
- *Light blend.* `normalize(sunDir·daylight + moonDir·(1 − daylight)·0.5)` for the sky light's
  direction, as specified, with the night/day values from §10.1 (plus the exposure and ambient
  changes listed in §9).
- *Interim brightening.* The `uExposure` stand-in from Phase 1b was replaced by Phase 2's
  exposure; nothing of it remains.
- *Pilot drone.* `↑`/`↓` forward and back, `←`/`→` turn (positive yaw turns left), `Space`/`Shift`
  up and down. The lean uses `pitchVis = +tilt · speed / maxSpeed` (the formula in §10.3 has the
  wrong sign: nose down is a positive `rotateX`).
- *Propellers.* Every drone has two crossed spinning blades per rotor plus a faint disc, not
  only the pilot drone.
- *Debug window title.* The Phase 1b title readout was replaced by the Phase 2 HUD.

### 10.1 Automatic day/night cycle

**Behaviour.** The scene runs a continuous 24-hour clock that advances on its
own, so day turns to night and back without any input. The scene opens at
night (the demo setting in PRD §5.1) and reaches dawn after about 50 seconds.
Key `N` cycles Auto → lock Day → lock Night, because the attenuation and
material-contrast demos (PRD §16.2) need a dark scene and shouldn't be at the
mercy of the clock.

**The clock** is a closed-form function of elapsed time, like every other
motion here, with no keyframe tables:

```
kDayLengthSeconds = 120          // one full 24 h cycle (tunable)
kStartHour        = 20           // opens at 20:00, night
hour(t)    = fmod(kStartHour + 24 · t / kDayLengthSeconds, 24)
theta(t)   = 2π · (hour − 6) / 24            // sun elevation angle: 0 at 06:00 and 18:00
sunElev    = sin(theta)                       // +1 noon, −1 midnight
sunDir     = normalize(cosθ·R + sinθ·U − 0.2·F)   // as built; see the notes above
moonDir    = normalize(−cosθ·R − sinθ·U + 1.3·F)
daylight   = smoothstep(−0.12, 0.25, sunElev) // 0 = full night, 1 = full day
twilight   = clamp(1 − |sunElev| / 0.25, 0, 1)// peaks at sunrise and sunset
```

With `P` (pause) the clock stops too, since it runs on simulated time. In a
lock mode, `daylight` eases toward 1 or 0 over about 1.5 s (so locking
doesn't snap the sky) and the clock is ignored.

**What changes with `daylight`.**

| Thing | Night | Day |
|---|---|---|
| Sky horizon colour | `(0.11, 0.12, 0.18)` (today's value) | `(0.62, 0.76, 0.90)` |
| Sky zenith colour | `(0.008, 0.012, 0.035)` (today's value) | `(0.18, 0.40, 0.78)` |
| Sunrise/sunset | — | Horizon mixed toward `(0.95, 0.50, 0.25)` by `twilight` |
| Stars | 220 visible | Alpha `= 1 − daylight` (fade out) |
| Moon | Today's sphere, now at `moonDir × 800` instead of a fixed direction | Fades to about 25% alpha |
| Sun | Hidden below the horizon | A bright disc at `sunDir × 800`, drawn only when `sunElev > −0.05` |
| Storm clouds | Today's dark shade | Shade raised by `0.35 · daylight` |
| Lightning | Strikes every 2.2 s, with a sky flash | **None.** No bolts and no sky flash while `daylight ≥ 0.25` (the sun is up). They return at dusk and stop at dawn |
| Window clear colour | Sky horizon colour | Same, so no dark band at the horizon |

**Interim brightening (Phase 1b only).** The terrain, trees, hut, windmill and
drones use dark flat colours picked for night, and would look wrong under a
bright day sky. Until real lighting exists, add a `uExposure` uniform that
multiplies the colour of those objects by `mix(1.0, ~4.0, daylight)`. Set it
to `1.0` for the self-lit things (lava, crater glow, droplets, lightning, sky,
stars) so they aren't blown out. This is a stand-in and is removed in Phase 2.

**Lighting terms *(Phase 2)*.** The directional light (Light 1 in §9.1)
follows the sky, and the scene stays at exactly two lights:

| | Night | Day |
|---|---|---|
| Direction `L` | from `moonDir` | from `sunDir` |
| `I_d` | `(0.12, 0.14, 0.20)` | `(1.00, 0.95, 0.82)` |
| `I_s` | `(0.15, 0.16, 0.18)` | `(0.60, 0.60, 0.55)` |
| `I_a_global` | `(0.04, 0.04, 0.06)` | `(0.28, 0.32, 0.40)` |

Blend `I_d`, `I_s` and `I_a_global` by `daylight`, and tint toward the warm
sunset colour by `twilight`. Blend the **direction** too, as
`normalize(sunDir · daylight + moonDir · (1 − daylight) · 0.5)`, so the light
never snaps from one side of the sky to the other when the sun and moon swap.
The crater light is unchanged. By day it is much less visible against the sun,
which is why the demos run on the night lock.

### 10.2 Views from the drones

**Behaviour.** Key `C` cycles the camera: free orbit → Drone 1 → Drone 2 →
Pilot drone (§10.3) → back. In a drone view the screen shows what that
drone's camera sees, from the gimbal position on its underside. This is the
viewing transformation in action, so it ties to the course content: the view
matrix is rebuilt each frame from a moving, rotating object.

**Aim modes** (key `V`):
- *Crater lock* (default): the camera looks at the crater, which is what a
  monitoring drone would do.
- *Forward*: the camera looks along the drone's heading, tilted down by the
  gimbal angle already modelled (35°).

**Maths.**

```
eye    = dronePos + (0, −0.2, 0) + heading · 0.3       // at the gimbal, just ahead of the body
target = craterPos                                      // crater lock
       | eye + R_y(yaw) · R_x(−35°) · (0, 0, 1)         // forward
view   = lookAt(eye, target, (0, 1, 0))
fov    = 70°    // wider than the orbit camera's 55°, like a real drone feed
```

**Required changes.**
- *Drones need a heading.* Today `drawResearchDrone(pos, time)` never rotates,
  so a drone doesn't face where it flies. Add a `yawRad` parameter and apply
  `Mat4::rotateY(yaw)` to the whole model (the camera sits on its `+Z` side).
  For the two orbiting drones, heading is the orbit tangent: velocity is
  `(−sin a, cos a)` for a positive speed and `(sin a, −cos a)` for a negative
  one, and `yaw = atan2(vel.x, vel.z)`. Optional: lean into the turn.
- *Hide the drone you're looking through,* or the camera sits inside its own
  body and the near plane clips it.
- *Use the active eye everywhere.* `drawSky` is given `g_camera.eyePosition()`,
  and Phase 2 uses the eye for `uViewPos` and the HUD's distance to the crater.
  All three must take the **active camera's** eye.

### 10.3 Controllable objects

**Primary: a keyboard-flown drone.** Add a **third drone**, the "pilot drone",

`(17, 14, 29)`, clear of the trees and flows.

| Key | While controlling |
|---|---|
| `Tab` | Take / release control. On take-over the orbit camera retargets to follow the drone |
| `↑` / `↓` | Forward / back along the heading |
| `←` / `→` | Turn left / right (yaw) |
| `Space` / `Left Shift` | Up / down |

Motion is simple kinematics, integrated each frame with `dt` so it doesn't
depend on frame rate:

```
speed   += (input − drag·speed) · accel · dt        // smooth start and stop
pos     += R_y(yaw) · (0, climb, speed) · dt
pitchVis = +tilt · speed / maxSpeed                  // visual lean into motion (nose down)
rollVis  = −tilt · yawRate / maxYawRate               // visual bank into turns
model    = T(pos) · R_y(yaw) · R_x(pitchVis) · R_z(rollVis) · parts…
```

Suggested constants: max speed 14 units/s, acceleration 18, yaw rate
90°/s, climb 8 units/s, tilt 12°. **Limits, not collisions:** altitude is
clamped to between a floor and 55 (below the storm layer at 62). The floor is
the larger of the ground and the cone surface plus a margin. The ballistic
code in `SceneObjects.cpp` already has `terrainHeightAt()`, which is `static`;
expose it. The distance from the volcano axis is also clamped. This is a
position clamp, not a collision system (PRD §3.2).

**Why this earns marks.** The drone is a transform hierarchy that the user
drives: body = `T·R_y·R_x·R_z`, each arm and rotor hub a child of the body,
each propeller a child of its hub and spinning with `R_y(ω·t)`, the gimbal a
child of the body. That is the composite and hierarchical categories again, on
an object the grader can steer. Make the propellers visibly spin (thin rotating
blades; the translucent static discs hide rotation) at least on this drone.

**Optional second object: a ground rover.** If a ground object is wanted too: a

None. Skip it unless time remains; the drone already covers the requirement.

**Frame-rate independence and the "no keyframes" rule.** Everything else in
the scene is a closed-form function of time. A controlled object cannot be,
because its position depends on past input. That is the one deliberate

## 11. Phase 3 — Ray tracing (hybrid) and inverse (light) ray tracing

**Built.** This was the stretch tier, built after the Phase 2 MVP worked, because it needs
lighting to exist first (a shadow removes a light term; a reflection has to be shaded). The key map
is in §4. This section is the specification; the code differs in these places.

**As built**
- *Emitters radiate in all directions.* The spec says cosine-weighted hemisphere about the
  surface normal. A flat strip of lava on the ground only shines upward, so almost no photon
  ever reached the ground (750 hits per frame). Flow samples are now a glowing line source,
  lifted 0.6 above the surface and emitting over the whole sphere: 2450 hits per frame, and a glow
  along every flow. The flows' emitter power is `width × length × (0.4 + heat)`; a droplet's
  is `6 × brightness`. Gain is 3 (`--gain` changes it).
- *Photon flux scales with the total emitted power* (`total / 4096` per photon), so more lava
  gives more light, instead of a normalised share.
- *Proxy scene.* Trees include their −10° lean (the cone is tilted about Z). The volcano is not an
  occluder for receivers within its footprint plus 1.5 units: a polygonal cone's facets lie
  inside the analytic cone, so surfaces on it would otherwise shadow themselves. The guide's
  reasoning (the crater light sits inside the cone) is why the volcano also never shadows the
  crater light.
- *Reflections* are on the lake (Schlick Fresnel, `F0 = 0.02`) and on the lava (constant 0.12).
  The reflected scene is the proxy shapes, the ground plane and the analytic sky; hills and
  mountains are not in it.
- *Gouraud while ray tracing is on* is evaluated per fragment, as specified.
- *Not built:* soft shadows, the diffuse photon bounce (§11.6 step 7).
- *A high noon sun casts no ground shadow of the volcano*: the sun is steeper than the cone's slope,
  so the cone's shadow falls on its own base. The shadow shows near sunrise and sunset
  (`--start 57.5` is 07:30).
- *Self-test.* `--selftest` checks the C++ intersections; there is no automatic GLSL comparison.

> **Scope warning.** The submitted proposal says *"No textures, shadows, or
> reflections will be used"*, and PRD §3.2 used to list both as non-goals.
> Ray tracing exists to produce shadows and reflections, so this directly
> reverses the proposal, as textures did (§7, decision 4). The report must say
> so plainly and keep the raster pipeline as the main renderer. PRD v1.3 has
> been updated to match (§3.1, §3.2, §4, §9.10–§9.11, §10, §14).

### 11.1 Two techniques, one toggle

| | Camera rays (ray tracing) | Light rays (inverse ray tracing) |
|---|---|---|
| Direction | Eye → pixel → scene → light | Light → scene → surface |
| Question it answers | What does this pixel see? Is it in shadow? What does it reflect? | Where does the light land? |
| Where it runs | GPU, in the fragment shader | CPU, once per frame |
| What it adds | Hard shadows from the sun/moon and crater; one reflection bounce on the lake and the lava | An orange glow cast onto the ground and slopes by the lava flows and the flying droplets |
| Key | `R` | `F` |

Naming note: the literature calls the camera-ray method *backward* ray tracing
and the light-ray method *forward* tracing. This project calls the second one
**inverse** ray tracing because it is the usual method run in reverse: it
starts from the light instead of the eye.

**Why hybrid and not a full ray tracer.** The program is OpenGL 3.3 core: no
compute shaders (those need 4.3), no recursion in GLSL, and the scene is
hundreds of meshes. So the raster pipeline stays the main renderer, and rays
are traced against a **small analytic proxy scene** of about a dozen shapes. The
proxy scene is deliberately simple: it is what casts shadows and shows up in
reflections, not what is drawn.

### 11.2 The proxy scene

Built each frame on the CPU from the same placement variables `main.cpp`
already uses, so there is one source of truth. Closed-form shapes only.

| Proxy | Shape | Dimensions (from the draw code) | Casts shadow from |
|---|---|---|---|
| Volcano | Truncated cone about the Y axis | Base radius 19, top radius 0.14 × 19 = 2.66, height 27 (`drawVolcano` scales the unit cone by `(R, H, R)`) | Sun/moon only (see below) |
| Burnt trees ×6 | Cone, sharp tip | Height `3.2 · scale`, base radius `0.22 · scale` (`drawBurntTree`) | Both lights |
| Hut | Oriented box (the walls) | About 3.2 × 2.0 × 2.6, rotated about Y by 295° (`drawBurntHut`) | Both lights |
| Windmill tower | Vertical cylinder | From `drawWindmill` | Both lights |
| Drones ×3 | Sphere, radius about 1.0 | Centre = the drone's position this frame | Both lights |
| Ground | Plane `y = 0` | — | (receiver, and a reflection target) |
| Lake | Ellipse on the plane | Centre `(-125, 0.11, -70)`, radii 30 × 20 | (reflective receiver) |

Left out on purpose: the forest, hills, mountains, storm clouds, ash cloud,
rim rocks and rock chunks. They are many, small or translucent, and would
multiply the cost for little visible gain.

**Why the volcano doesn't shadow the crater light.** The crater light sits
inside the cone's top (`craterPos` is at y = 25.1, inside the 2.66-radius
mouth), so a shadow ray from any slope to the crater would pass through the
solid proxy and shadow the whole mountain. The crater light is treated as a
local glow at the vent that the cone does not block. The volcano still
shadows the sun and the moon.

### 11.3 Camera-ray tracing: shadows and reflections

Runs in the fragment shader, once `uRTMode` is above 0. `R` cycles
**Off → Shadows → Shadows + Reflections**.

**Intersection tests** (all closed form; the C++ and GLSL versions must agree):

```
sphere (centre c, radius r):   oc = o − c;  b = oc·d;  h = b² − (oc·oc − r²);  t = −b − √h        (h > 0)
plane  y = 0:                  t = −o.y / d.y                                                      (t > 0)
box (slab test):               t_near = max over axes of min((lo−o)/d, (hi−o)/d);  t_far = min of max(...)
                               (rotate the ray into the box's local frame first; the hut is rotated)
cone / cylinder about Y, radius r(y) = r0 + k·(y − y0), k = (r1 − r0)/h, with q = r0 + k·(o.y − y0):
    a = dx² + dz² − k²·dy²      b = ox·dx + oz·dz − k·q·dy      c = ox² + oz² − q²
    t = (−b ± √(b² − a·c)) / a          accept only if y0 ≤ o.y + t·dy ≤ y0 + h
```

(`o` is relative to the shape's axis origin. A cylinder is the `k = 0` case, and
a tree trunk is the `r1 = 0` case.)

**Shadows.** For each light, per fragment, when `N·L > 0`:
- Origin `P + N · 0.03` (an offset to avoid self-hit "acne"); direction `L`.
- The sun/moon uses its constant direction; the crater uses `normalize(craterPos − P)` and a maximum distance equal to the distance to the crater.
- Any hit on an allowed occluder (table above) means shadowed: multiply **that light's diffuse and specular** by 0. Ambient and emission are untouched.
- The sun at a low angle (dawn, dusk) gives the long volcano shadow across the plain, and the shadow turns with the clock (§10.1).

**Reflections.** Surfaces carry a `uReflectivity` (a new field on the material, §9.4):

| Surface | Reflectivity |
|---|---|
| Lake | Schlick Fresnel with `F0 = 0.02`: `F = F0 + (1 − F0)·(1 − N·V)⁵`. Grazing views reflect strongly |
| Lava (flows, droplets) | Constant `0.12`, to match the glossy `n_s = 140` look |
| Everything else | 0 |

For a reflective fragment: `R = reflect(−V, N)`, trace once against the proxy
scene. A hit is shaded cheaply (`albedo · (ambient + sky-light · max(0, N·L))`,
no shadow ray, no second bounce). A miss returns the **analytic sky colour**
for direction `R`, using the same formula as the sky dome:

```
sky(R) = mix(uHorizon, uZenith, smoothstep(0, 0.75, R.y))  + sun disc  +  moon disc
```

with `uHorizon`/`uZenith` from the day/night state (§10.1). Because it is
analytic, the lake mirrors the current sky: the stars and moon at night, the sun
and blue sky by day. Final colour: `mix(lit, reflected, F)`.

**Interaction with shading modes.** Ray-traced terms need the lighting evaluated
per fragment. So **when `uRTMode > 0`, Gouraud is evaluated per fragment too**
(it looks like Phong), and Flat keeps its face normal. The shading demos (Demo A
and Demo B, §9.2) run with ray tracing off. This is the price of keeping one
shader.

**Cost control.** Roughly 0.9 M pixels × 2–3 overdraw × (two shadow rays and one
reflection ray) × about 12 shapes is tens of millions of intersection tests per
frame, which is fine on a discrete GPU and borderline on integrated graphics.
So: skip the whole block when `uRTMode == 0` (a uniform, so the branch is
coherent); skip a light when `N·L ≤ 0`; skip fragments more than about 300
units from the volcano; keep shadows-only as a cheaper mode than shadows +
reflections; and measure before adding soft shadows (4 jittered rays).

**Honest limit: at night the shadows are weak.** The moon is dim and the
crater light is strongly attenuated at the trees and hut (about 3% at distance
40). So the **sun-lit day** is where shadows show; use the day lock for that
demo, and the night lock for the lava glow in §11.4. Reflections show well at
both times.

### 11.4 Inverse ray tracing: light rays from the lava

Each frame, on the CPU, fire photons from the glowing things, trace them
through the proxy scene, and record where they land. The result is a **light
map**: a top-down grid of irradiance that the shaders read to add the lava's
glow to the ground, slopes and nearby objects. Nothing in the raster path
lights the surroundings from the lava today.

**Emitters.**

| Emitter | How it emits | Power |
|---|---|---|
| Lava flows (×5) | 16 sample points along the advanced part of each path (`u ∈ [0, advance]`); cosine-weighted hemisphere about the surface normal | `width × (0.4 + heat)` |
| Lava droplets (×8) | From each droplet's current position, uniformly over the sphere | Its brightness × its cooled scale |
| Crater glow disc | **Not used.** It sits inside the cone and its rays go up and escape, so the crater's effect on the ground stays in the Phong light | — |

**Tracing.** `N = 4096` photons per frame, split among emitters by power, with
the direction chosen by a hash of `(frame · N + i)` (deterministic, no stored
random state). Each photon traces against the same proxy scene as §11.2 plus
the ground. On a hit:
- Ground, lake or volcano slope: deposit into the light map (below) and stop.
- Tree, hut, windmill or drone: absorb (so shadow-shaped gaps appear behind them).
- Optional stretch: one diffuse bounce by Russian roulette, which gives soft colour bleeding.

**Light map.** A `128 × 128` float grid covering ±160 units around the volcano
(2.5-unit cells), stored as an `RGB16F` texture on texture unit 1. The terrain
and the volcano are a height field over `(x, z)`, so one top-down grid covers
both.

```
deposit(cell) += photonPower · n_y / A_cell          // flux per surface area; the cosine is already in the photon density
map = (1 − α)·map + α·thisFrame                      // α ≈ 0.15, to smooth the noise over a few frames
```

Splat bilinearly into the four neighbouring cells. Photons carry the emitter's
colour (orange for lava). Upload with `glTexSubImage2D` each frame (49 k floats).

**Use in the shader.** For any lit fragment, add the glow as another light term:

```
colour += albedo · texel · texture(uLightMap, (P.xz − mapOrigin) / mapSize + 0.5).rgb · uPhotonGain
```

Tall objects (trees, hut, drones) sample the map at their base position: an
approximation. `uPhotonGain` is a tuning constant. By day the sun swamps the
glow, which is physically right. The `F` key toggles it; `M` draws the map as a
small minimap in the corner for debugging and for the report.

**Why this is "inverse" tracing, and what it demonstrates.** It is the same
intersection code as the camera rays, run from the light. Forward density falls
off as 1/d² on its own, so the attenuation the PRD gets from `1/(a₀ + a₁d + a₂d²)`
for the crater light comes out of the geometry here. Obstacles cast their
shadows as empty regions in the map rather than through a shadow test.

## 12. Eruption bursts

The smoke used to be a static ash umbrella plus six small puffs, so the volcano never visibly
*erupted*. It now bursts. Everything below is a closed-form function of time (`src/Eruption.h`),
so nothing is stored or pre-recorded.

### 12.1 The burst schedule

```
burst b starts at   t_b = 1.5 + 9 · b            seconds (every 9 s)
envelope(τ)         = τ / 0.35                   rising to the peak in 0.35 s
                    = exp(−(τ − 0.35) / 2.2)     then decaying
amp_b               = 0.75 .. 1.0, and every third burst is 30% bigger
intensity(t)        = Σ over the latest three bursts of amp_b · envelope(t − t_b)    (capped at 1.5)
plume(t)            = Σ over the latest five bursts of amp_b · (1 − e^{−τ/0.8}) · e^{−τ/6}
```

Bursts fired with the `E` key (§13.5) join this list as extra, always-big bursts, and everything below
reacts to them in the same way.

### 12.2 What reacts to a burst

| Thing | Behaviour |
|---|---|
| **Smoke plume** (`drawEruptionSmoke`) | 22 puffs per burst, 0.035 s apart. Each leaves the vent within about 25° of vertical at 14–26 units/s × the burst's size, slows under drag (`distance = v·(1 − e^{−0.75 τ}) / 0.75`), rises on a steady buoyancy and drifts downwind. It swells from radius 1.2 to about 5.6, fades in over 0.12 s and out over 10 s, and **cools from glowing orange (emissive) to grey** as `e^{−τ/0.9}`. Only the current and the previous burst are drawn |
| **Vent flash** | In the first 0.75 s of a burst, two translucent expanding fireballs (a white-hot core and a wider orange shell) |
| **Ash umbrella** (`drawAshCloud`) | Its size scales with `0.62 + 0.5·level` and its height with `0.75 + 0.35·level`, where `level = 0.35 + plume(t)`: it swells and climbs after a burst and thins before the next |
| **Crater light** | Multiplied by `1 + 2.5 · intensity`, so the vent flares and lights the slopes, the rim and the smoke |
| **Lava fountain** | Droplets spawn up to 4× faster and 80% harder; rock chunks 4× faster and 60% harder |
| **HUD** | `ERUPTION: BURST 70%` while above 15%, otherwise `NEXT BURST IN 5.2 S` |

### 12.3 Verified

Rendered at 1.3, 2.05, 3.5 and 6.5 s at night and 1.65, 2.6 and 4.5 s by day: before the first burst
only the quiet baseline; then the fire flash; then a glowing column rising and spreading under the
cloud layer; then the column cooling to grey. Frame rate with everything on is 74 FPS (about 1150
draw calls). The visual effect is judged from still frames, since a script cannot play the animation
live; `--start <sec>` jumps to any moment.

were **removed on 2026-10-11**: the smoke came out of the vent, came down the slope and spread over the whole ground,
which does not read as realistic in this scene. `drawPyroclastic` and its call are gone, and `drawEruptionEffects` no
longer takes the volcano's height. A big burst now differs from an ordinary one only by its size, its extra lake bombs
(§13.4) and the stronger shockwave and shake that its size gives.

### 13.2 Shockwave and camera shake

- **Shockwave.** Every burst sends two expanding rings across the ground from the foot of the cone:
  `radius = 19 + 52 · tau` (the second ring 0.15 s behind and 7 units inside), thickness a fixed 14% of the
  radius (a unit ring mesh scaled by the radius, `Geometry::ring`), fading as `(1 − tau/3.2)^1.5` over 3.2 s.
  Unlit pale orange, alpha-blended.
- **Camera shake.** At the start of every burst the view jolts and settles: a rotation of up to
  `0.011 · amp` radians (about 0.6°) about x, y and z at different frequencies (63, 79 and 51 rad/s), scaled by
  `Eruption::shake(t) = Σ amp · e^{−(t − start)/0.55}` so it dies away in about a second. It is a rotation
  of the **view** only: the eye does not move, so distances, the HUD and the ray-traced reflections are
  unaffected. `J` turns it off. Checked by comparing frames: 7% of pixels move at the instant of a burst and
  none move when it is quiet.

### 13.3 Volcanic bombs with glowing trails (`SceneObjects.cpp`)

The larger rock chunks (size above 0.86 of the 0.55–1.05 range, about a third of them) are **bombs**:
35% bigger, white-hot at the vent and cooling to rock as `heat = e^{−age/2.2}` (colour and emission both),
and in flight they drag a trail of 12 glowing puffs. The trail is made of the bomb's own earlier positions:
the ballistic formula evaluated at `age − k · 0.05 s` for `k = 1..12`, each smaller and fainter than the last. A
bomb keeps glowing faintly after it lands.

### 13.4 Lake bombs, splash and ripples (`Effects.cpp`)

The lake is about 143 units from the vent and ordinary ejecta fly only about 60, so nothing ever landed in
it. A **big** burst therefore throws a salvo of two long-range bombs at random points on the lake. The launch
speed is **solved** so each lands on its target (horizontal distance `D`, elevation `theta` = 36–46°, launch
height `h0`, water level `hw`):

```
T = sqrt( 2 · (h0 − hw + D · tan(theta)) / g )        time of flight, about 4.9 s
v = D / (T · cos(theta))                              launch speed, about 29 units/s
```

Each bomb is a tumbling white-hot rock with a 16-puff trail. At the impact, as a function of the time `tau`
since it landed:

| Part | Behaviour |
|---|---|
| Fire flash | An orange fireball for 0.3 s |
| Ripples | Four rings, 0.28 s apart, expanding at 3.1 units/s to a radius of 7 and fading over 2.4 s |
| Spray | 12 droplets thrown up (4–7 units/s) and out under gravity; **each makes its own small ripple where it falls back** |
| Steam | 7 puffs rising and spreading over 4 s (molten rock meeting water) |

### 13.5 Trigger key

`E` fires an extra **big** burst at the current simulated time (`Eruption::trigger`). The schedule stays
closed-form: the key only adds a start time to a short list (the last 8 are kept), and `Eruption::recent`
merges that list with the scheduled bursts, sorted by start time. Everything above is evaluated from that merged
list, so a fired burst gets the smoke plume, the shockwave, the shake, the bombs and the
lake splash, exactly like a scheduled big burst. Pressing `E` while paused starts the burst when you unpause.
`--fire <t>` does the same from the command line.

### 13.6 Verified (2026-10-09)

- Rendered a fired burst at 0.5, 1.6, 3.2 and 6 s: the shockwave rings, the plume and the bombs' trails (the
  pyroclastic flows that were also drawn here have since been removed, §13.1). Four rings were confirmed drawn at the
  expected radii (41, 56, 67 and 82 at one moment) by logging them.
- Rendered the lake around the impact: a bomb with its trail falling in, then ripples, spray droplets and steam
  at both impacts (the first version's steam was far too big and solid, and was tuned down).
- Camera shake confirmed numerically (above). No GL errors with a fired burst under Gouraud with shadows,
  Phong with ray tracing and lava-light tracing, the pilot camera, and the helicopter under autopilot.
- Frame rate: 285 FPS by day (927 draw calls); **65 FPS in the worst case**, with three overlapping big
  bursts, ray tracing and lava-light tracing on (1363 draw calls).
- **Bug found and fixed:** the first `--fire` implementation took the address of a loop copy to build the burst's id,
  which gave a garbage id (the id only seeds the hashing, so nothing visibly broke).
- **Not tested by hand:** the `E` and `J` key presses themselves.

### 13.7 Not done

Ordinary lava droplets and rock chunks never reach the lake (they land within about 60 units), so only the lake
bombs splash. Ripples on the lake from the boat's wake and from the helicopter's downwash, a ground
crater where a bomb lands, and burning the trees the flows pass over are all unbuilt.

## 14. Lava pool and draw order (fixes, 2026-10-11)

Two things were reported from a run: *"a constant orange circle on the ground of lava, inconsistent"* and
*"from above the clouds the helicopter and the ground rover are seen, which is not realistic"*. Both were real bugs.

### 14.1 The lava pool is now a basin that the sheet flow pours into

**What was wrong.** The pool was a single flat orange disc at a fixed spot `(-44, 0.1, 6)` with no flow leading to
it, present from the first frame and only growing slowly. Nothing moved on it, and it fed nothing.

**What it is now** (`drawLavaPool`):

| Part | Behaviour |
|---|---|
| Position | The end of the **broad sheet flow** (the last `LavaFlowStyle`, azimuth 322°) plus 4.5 units outward: about `(52, 0.1, -41)`. The flow runs straight into it |
| Arrival | It does not exist until the flow reaches it. It fills as `R = 7.5 · smoothstep(t_a − 3, t_a + 22, t)`, where `t_a = (1 − 0.25) / growSpeed` is when the flow's advance reaches 1 (about 25 s). The sheet flow's `growSpeed` went from 0.020 to 0.030 so it arrives sooner |
| Cooled crust | The whole disc, dark red, lightly emissive |
| Molten core | 82% of the radius, bright orange. It flickers (`sin(2.1 t) · sin(0.7 t + 1)`) and its radius breathes by 3% |
| Inflow glow | A hot patch on the side facing the volcano, half way out, that pulses with the same travelling wave as the flow |
| Crust plates | Ten dark matte slabs carried round by the circulation (`angle += 0.16 · (1.15 − r/R) · t`, faster in the middle), each growing, breaking up and re-forming (`0.6 + 0.4 sin(0.35 t + phase)`) |

The crust and the core are still the `poolDisc` mesh, so `+` and `−` change their tessellation and the
Gouraud-vs-Phong highlight demo (Demo A, §9.2) still works on it. **Demo A's camera position changed** with the pool: the
glint is at the sun's mirror point on the pool at about `(52, 0.1, -41)`.

Two smaller changes in the same fix: the travelling brightness pulse along every flow is more visible
(amplitude 0.10 → 0.22), and the lobes at the end of a flow now breathe by ±7% so a flow front keeps moving.

### 14.2 Draw order: nothing solid shows through the cloud layer

**What was wrong.** The 80 storm-cloud puffs at `y ≈ 62` were drawn *before* the vehicles. Translucent puffs do
not write depth, so a rover or helicopter drawn afterwards was painted over them, and looking down from above the
layer (a free camera orbits as high as 300 units) you saw the rover and the helicopter through a solid deck of cloud.

**What it is now** (`renderScene`):

1. **Opaque pass:** the sky dome, terrain, volcano, crater, rim rocks, pool, lava flows, droplets, rock chunks, trees, hut,
   windmill, helipad and every vehicle. Everything here writes depth.
2. **Translucent pass, back to front, no depth writes.** Which end of the pass the storm layer sits at depends on the
   camera: it is the *farthest* thing for a camera below it (drawn first) and the *nearest* for a camera above it
   (drawn last). So below `y = 62` the order is storm clouds, lightning, then the eruption's effects, ash puffs, smoke
   plume and ash umbrella; above it, the reverse. Every vehicle is already in the depth buffer, so a vehicle under the
   layer is correctly covered by it.
3. The cloud puffs are also a little more opaque (`0.88 → 0.95` alpha), so one puff hides what is behind it (a deck of
   several puffs hides it completely).

### 14.3 Verified (2026-10-11)

- *Lava pool:* rendered at 14, 26, 40 and 80 s. At 14 s only the flow's tip has reached the basin and the pool does not
  exist; at 26 s the pool has just begun to fill; at 40 s it is a full pool with a hot core, a glowing inflow patch and
  dark crust plates; at 80 s the flow still feeds it. By night the crust plates and edge read clearly.
  **Not seen live:** the plates' drift and the core's flicker. Those come from still frames and the formulas.
- *Clouds:* the same top-down frame (camera at 140 units, pitch 80°) rendered with the old and new builds: **82 yellow
  rover pixels before, 0 after**; the helicopter is a faint shadow under the deck instead of a clear object.
- Self-test passes, no GL errors in five configurations (Gouraud with ray tracing and lava-light tracing, Flat with shadows,
  the rover camera, a fired burst, Blinn at low tessellation), 205 FPS at 915 draw calls by day.
- *Still faintly visible:* with the camera right above the layer a vehicle can show as a faint grey ghost through one thin
  patch of cloud. That is a translucent layer behaving as it should, not a draw-order bug.

### 14.4 Not done

The pool does not receive photons from the lava-light tracing as a separate emitter (the flow samples cover its
inflow), the drifting crust plates are not in the ray-tracing proxy scene so they cast no shadow, and the other four
flows still just end at a point. (The long river ends in a lobed front and the others taper.)

## 15. Driving keys moved off the letters (2026-10-11)

`S` was hard to type, so **no letter key is used to drive any more**. The arrow keys drive whichever object `Tab`
selected (`↑` forward, `↓` back, `←` / `→` turn), and `Space` / `Left Shift` still climb and descend. Because
the arrows used to orbit the camera, orbiting moved:

| Camera orbit | When |
|---|---|
| Arrow keys | Only while **nothing** is controlled (as before) |
| `Z` / `X` (yaw) and `Home` / `End` (pitch) | Always |
| Left mouse button dragged (0.25° per pixel) | Always. It needs no cursor capture |

The old `W`, `A`, `S` and `D` do nothing now. Nothing else in the program used them.

### 15.1 Verified with real key presses

Earlier rounds could only test input through command-line options. This time key presses were injected into the
running window (focus confirmed, `--bench` printing the controlled object's final position and the camera angles):

| Input | Result |
|---|---|
| no key | rover stays at (-28, -2) |
| `↓` held 4 s | rover reversed to x = -44 |
| `↑` held 4 s | rover drove toward the volcano and stopped at its 22-unit keep-out radius |
| `S` or `W` held | no movement |
| `←` held while stationary | no change (the rover only steers while moving) |
| `X` held 1.5 s | camera yaw 35° → 125° |
| `Home` held 1 s | camera pitch 10° → 71° |
| `↑` with nothing controlled | camera pitch changes (the arrows still orbit) |
| Left mouse drag | camera yaw and pitch change |

**Not verified:** the mouse sensitivity. Windows display scaling rescaled the injected cursor positions, so the
size of the response to a drag could not be checked. The letter-key handlers (`Tab`, `E`, `N`, ...) were not
re-tested this round; they were not changed.

## 16. The rover collides and bumps (2026-10-11)

**Reported:** the rover drove straight through rocks, trees and everything else. Nothing in the scene had a
collision shape; the only limit was a silent radius clamp around the volcano.

### 16.1 Obstacles

Every obstacle is a **circle on the ground** (`Collider.h`: x, z, radius, kind). The rover is a circle of radius 1.5
(its body is 1.7 wide and 3.0 long), so a collision test is one distance comparison. The shapes are built from the same
numbers as the draw code, so a collider is always where its object is drawn:

| Obstacle | Shape |
|---|---|
| Burnt trees (6) | trunk circle `0.4 × scale`, plus two debris rocks at the foot (the same hash as `drawBurntTree`) |
| Burnt hut | three overlapping circles of radius 1.3 along its width, rotated with the hut, plus its three debris rocks |
| Windmill | its stone footing, radius 0.85 |
| Healthy forest (about 85 trees) | `0.9 × scale` each. The placement code was pulled out of `drawTerrain` into one helper, so a tree that is drawn is also solid |
| Rocks | every rock chunk that has **landed** and is resting on the ground (they last 4 s), radius `0.8 × size` |
| Helicopter | a circle of radius 2.0 while it is parked (`y < 1`); a flying one passes overhead |
| Volcano | its footprint (radius 19.5). This replaces the old silent clamp at radius 22 |
| Lake | an ellipse 31 × 21 around the water; the rover cannot drive into it |
| World edge | radius 150 |

Not obstacles: lava (the rover drives over it), the helipad (flat), hills and mountains (too gentle or too far), the
rim rocks and the other drones.

### 16.2 What happens on a hit (`Rover::update`)

1. **Resolve:** the rover is pushed straight out of the overlap along the contact normal.
2. **Reflect:** `v' = v − (1 + e)(v·n)n` with a restitution `e = 0.35`, then only the part along the heading is kept (a
   rover cannot slide sideways). A head-on hit at speed *v* sends it back at 0.35 *v*; a glancing hit slides it along
   the obstacle.
3. **Bump** (only if the impact speed is at least 1.2 units/s and 0.25 s has passed since the last bump, so pressing
   against an obstacle does not retrigger):
   - the nose **swings away** from a glancing blow (a yaw kick);
   - **three damped springs** (`x'' = −kx − cx'`) react to the impact speed: a **nose dive** on a head-on hit (a lift if
     hit from behind), a **roll**, and a **hop**;
   - a **camera jolt** is added to the eruption shake, but only while you are driving the rover or looking through
     its camera;
   - the HUD shows `BUMPS n (WINDMILL)` for 3 s.

### 16.3 Verified (2026-10-11)

| Test | Result |
|---|---|
| Real `↑` key held, rover facing the windmill | stopped at x = −42.2 (the footing's contact point is −42.25) after an impact of 7.9 units/s |
| Real `↑` held toward the hut | stopped against the debris rock in front of it, bump `ROCK` |
| Real `↑` held on open ground | no bump |
| Physics alone, head-on at 7.9 units/s | reversed at 2.76 units/s, nose dive 0.21 rad (12°), hop 0.21 units, shake 1.1, settled in 0.5 s |
| Physics alone, glancing | the nose swung away (yaw 1.571 → 1.474) and the rover slid clear |
| Toward the lake and the volcano | stopped at the shore (x = −94) and at the cone's footprint (x = −21), one bump each |
| Self-test and GL errors | pass |

**Not verified:** how the bump *looks* in motion. The checks above are numbers and a few still frames in which the
camera follows the rover, so the dive and hop are hard to see. Judge that live.

### 16.4 Not done

The other vehicles do not collide (the drone and helicopter fly; the boat is held inside the lake by a clamp, not a
bump), and the rover's rock/tree obstacles are circles, so a corner of the hut can still be driven into slightly. Sounds,
dust on impact and driving through lava are not built.

## 17. HUD clean-up (2026-10-11)

Removed from the on-screen panel: `ACTIVE DROPLETS`, `ACTIVE ASH PUFFS` and `LAVA RIVER ADVANCE`, together with the
code that counted active ash puffs and exposed the counts (`activeLavaDroplets`, `activeAshPuffs`).

The `[key]` hints at the end of each panel line were removed in the same change by mistake (they were read as
"redundant" labels), and **restored the same day** at the user's request. They are back exactly as before, next to the key
legend along the bottom of the window.

What the panel shows now (top to bottom): shading, lights, terms, specular model, cone segments, textures, ray tracing,
lava-light tracing, time of day, camera, then the eruption countdown or burst strength, the distance to the crater, the
controlled object with its speed and (rover) bumps, and the frame rate with the draw-call count.

Note that `s_activeDroplets` stays: the lava-light tracing uses it to know how many droplets to emit photons from.
Sections of this guide written before this change (for example §9.4's HUD description and the verification notes) may still
mention the removed lines; this section supersedes them.
